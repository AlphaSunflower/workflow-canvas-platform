# 全局执行运行态重构说明

## 1. 文档目的

本文档用于冻结前端“真实后端节点执行运行态”重构范围，明确本轮重构不是对白模渲染节点做一次临时性能修补，而是建立一套后续所有真实后端节点都复用的统一执行运行态基础设施。

本文档解决三个问题：

- 哪些状态属于工作流结构状态，哪些状态属于执行运行态。
- 当前卡顿问题的根因是什么，为什么不能继续把高频执行态塞回 `WorkflowContext`。
- 后续所有真实后端节点必须通过什么方式接入统一执行链路。

## 2. 本轮重构结论

本轮重构已经冻结以下原则：

- 工作流结构状态和执行运行态必须分层。
- `WorkflowContext` 不再承担高频轮询状态容器职责。
- 节点组件不得自行编写轮询循环、递归轮询或局部轮询定时器。
- 所有真实后端节点统一走三层基础设施：
  - `ExecutionRuntimeStore`
  - `ExecutionPollingManager`
  - `ExecutionOutputCommitService`
- 白模渲染节点只是第一个接入节点，不允许继续发展为白模专用架构。
- 后续节点只能通过“节点执行适配器”扩展，不允许继续在 `WorkflowContext` 里堆节点专用分支。
- 本轮不处理后端 worker 并发策略，不处理 API key 池调度，不处理后台管理 UI。

## 3. 当前问题与根因

此前前端执行链路存在以下问题：

- `WorkflowContext` 同时承担工作流结构读写、任务创建、轮询、执行态缓存和输出回写。
- 高频执行态直接挂在上下文内，导致执行进度变化会驱动整张画布相关消费者重新渲染。
- 白模节点把执行态字段拼进 `inputLayoutVersion`，导致 `updateNodeInternals()` 在轮询过程中高频触发。
- 轮询和输出回写耦合在同一条链路里，已完成 group 容易被重复 append，进一步放大结构刷新。

结论很明确：当前卡顿的根因不是某个节点组件“代码写得慢”，而是执行运行态被错误地放进了工作流主上下文，并与布局重算耦合。

## 4. 状态分层边界

### 4.1 工作流结构状态

工作流结构状态只包含低频、可持久化、与画布结构直接相关的数据：

- 节点列表
- 连线列表
- 视口
- 节点配置
- 输入组结构
- 结果文件真正回写后的节点/连线变化
- 保存、加载、快照、导入导出相关元数据

这些状态继续由原有工作流能力负责。

### 4.2 执行运行态

执行运行态只包含高频、短生命周期、不应直接视为画布结构的数据：

- run 级状态
- task 级状态
- node 级摘要
- group 级状态
- 当前步骤
- 当前 attempt
- retry 状态
- 错误摘要
- 终态结果是否可提交、是否已提交

这些状态统一进入 `ExecutionRuntimeStore`，不得再直接挂进 `WorkflowContext` 主渲染链路。

### 4.3 输出回写边界

输出回写是执行运行态落回工作流结构状态的唯一合法出口。只有满足以下条件时才允许改动画布结构：

- 后端返回了终态结果文件。
- 结果文件尚未写回。
- 当前任务或 group 的结果符合提交条件。

执行中的进度变化、步骤变化、attempt 变化都不应触发结构层刷新。

## 5. 统一架构

### 5.1 ExecutionRuntimeStore

职责：

- 持有 run、task、node、group 四层运行态。
- 按 `workflowId / nodeId / groupId / taskId` 做细粒度索引。
- 支持按键订阅，只通知命中的运行态消费者。
- 支持按 workflow 清理，避免多画布执行态串污染。

当前已落地能力：

- `subscribeRun`
- `subscribeNode`
- `subscribeGroup`
- `subscribeTask`
- `applyRunSnapshot`
- `applyPatches`
- `reset`

### 5.2 ExecutionPollingManager

职责：

- 统一管理 run 级轮询生命周期。
- 一个 `runId` 只允许存在一个轮询任务。
- 统一管理 `AbortSignal`。
- 统一把后端快照转为运行态 patch 并写入 Store。
- 终态自动停止。

当前已落地能力：

- 同 run 去重启动
- 终态自动结束
- `stop / stopAll`
- 自定义 `mapSnapshotToPatches` 扩展入口

### 5.3 ExecutionOutputCommitService

职责：

- 在统一时机提取终态输出。
- 做结果提交去重，避免重复 append。
- 将结果真正写回工作流结构。
- 将“已提交”状态同步回运行态 Store。

当前已落地能力：

- 支持 grouped 节点增量回写
- 支持 terminal-only 模式
- 支持 run/task/group 级提交状态回写
- 支持按 `runId + taskId + groupId + resultFileId` 去重

### 5.4 Node Execution Adapter

职责：

- 校验节点输入是否可执行
- 构建执行请求 payload
- 映射后端快照到运行态 patch
- 提取终态输出

当前已落地能力：

- 已定义统一 adapter 接口
- 已建立注册表机制
- 白模渲染节点已作为第一个适配器接入

## 6. 本轮已完成的结构性改动

- 新增独立执行态目录：`src/execution-runtime/`
- 建立全局 `ExecutionRuntimeStore`
- 建立统一 `ExecutionPollingManager`
- 建立统一 `ExecutionOutputCommitService`
- 建立节点执行适配器注册表
- 白模节点已切入统一执行链路
- 白模节点布局版本计算已剥离执行态字段

## 7. 性能收益预期

本轮重构的目标不是“让轮询更快”，而是“让轮询更新只影响必要的订阅者，不再推动整张画布一起重渲染”。

预期收益：

- group 级状态更新不再触发整张画布布局重算
- 白模节点运行时拖拽、缩放、选中明显更稳定
- 已完成结果不会被重复 append
- 后续新节点接入时不需要再复制一套轮询和状态管理逻辑

## 8. 本轮不做项

本轮明确不做以下内容：

- 后端并发策略调整
- 后端排队策略调整
- API key 池管理策略调整
- 后台管理 UI
- 非真实后端节点的统一迁移

## 9. 验收标准

本轮重构完成后，至少应满足：

- `WorkflowContext` 不再承担高频执行态存储职责
- 前端存在唯一轮询入口
- 前端存在唯一输出回写服务
- 白模节点进度变化不再驱动布局版本变化
- 执行态基础设施有自动测试覆盖
- 后续节点可按统一 adapter 规范接入，无需重新设计执行架构
