## 2. 项目现状判断

### 2.1 当前真实技术基线

以当前仓库代码为准：

- 前端：`Vite + React 18 + TypeScript + ReactFlow + Zustand`
- 后端：`TypeScript / Node.js`，目录为 `backend/api + backend/worker + backend/shared + backend/db`
- 存储：当前是 `workflow JSON Store + 本地 blob 存储 + SQL migration 基线` 的混合形态
- 已有节点基础：
  - `aiImageGen`
  - `aiStoryboard`
  - `aiVideoGen`
  - `aiImageToPly`
  - `aiMultiViewRestore`
  - `aiModelRenderTransfer`
  - `aiImageHd`
  - `aiFloorplanColorize`

### 2.2 当前已经具备的能力基础

当前仓库已经不是纯前端原型，已经有以下可复用基础：

- 工作流画布后端化基础
- 文件注册、上传、预览、缩略图链路
- 执行主记录、任务记录、事件流、重试机制
- `AI 提示词补全` 与 `Storyboard Arrange` 的多模态服务基础
- `aiImageHd`、`aiImageToPly`、`aiFloorplanColorize` 等节点协议文档和部分真实执行链路
- 任务历史、快照关联、数据库、中台的基线文档

### 2.3 当前约束

当前也存在几个必须正视的约束：

- `backend/admin-web/` 目录尚未真正落地，中台还是规划态
- 前端存在 `WorkflowContext.tsx`、`Canvas.tsx` 等架构热点，继续向大文件堆逻辑会放大后续维护成本
- 数据库存储仍然是混合态，稳定领域和画布领域还需要进一步冻结边界
- 新功能数量较多，若没有并行开发线，2 个月周期会非常紧

### 2.4 本计划的关键结论

本轮开发必须遵守以下判断：

1. 后端继续沿用当前 `TypeScript / Node.js` 架构，不做 “切回 Go 重写后端” 这类高风险重构。
2. 所有新节点与新智能体必须复用现有 `workflow / file / execution / task / event` 主链路。
3. 必须先补齐数据底座和管理中台，再推进高复杂度的 3D、全景与智能体功能。

## 5. 核心架构建议

## 5.1 后端架构原则

本期保持以下后端结构不变：

```text
backend/
  api/
  worker/
  shared/
  db/
  docs/
  runninghub/
```

执行原则：

- `api/` 负责鉴权、工作流、文件、执行、任务查询、中台接口、AI 辅助同步接口
- `worker/` 负责异步节点执行、Provider 调用、重试、产物保存
- `shared/` 负责共享常量、DTO、节点类型、模型配置契约
- `db/` 负责 migration 与数据库结构基线

## 5.2 数据存储策略

本期不建议强行把全部工作流结构一次性完全关系化，而是继续采用“稳定领域 SQL 化，画布领域分片存储化”的混合策略：

1. 继续保留 `workflow` 的 JSON Store / 分片持久化
2. 强化以下稳定领域的数据结构：
   - 用户
   - 文件
   - 执行
   - 任务
   - 任务事件
   - 审计日志
   - 模型注册
   - 智能体会话
3. 文件存储继续使用统一内容寻址 blob 目录，后续可平滑切换对象存储

## 5.3 本期建议新增或补齐的数据结构

在当前已有表与分片基础上，本期建议新增以下结构：

### 关系型表

- `model_registry`
  - 记录模型编码、Provider、适用节点、质量等级、是否启用、默认状态、并发限制
- `workflow_snapshots`
  - 保存画布快照主记录
- `workflow_snapshot_tasks`
  - 保存快照与任务关联
- `agent_sessions`
  - 按 `workflowId` 保存智能体会话
- `agent_messages`
  - 保存消息历史、角色、模型、上下文摘要
- `agent_artifacts`
  - 保存智能体生成的提示词草稿、规划结果、调研报告等
- `admin_metrics_daily`
  - 用于中台首页聚合展示

### 字段扩展

- `file_assets.file_type`
  - 从当前偏图片类型扩展为至少支持：
    - `image`
    - `mask`
    - `panorama`
    - `ply`
    - `splat`
    - `video`
    - `document`
- `execution_tasks`
  - 补充节点级 `payloadVersion` 或同等版本标识，避免新节点协议演化后回放困难

## 5.4 节点形态策略

本期新能力建议分成两种节点形态：

### 轻量节点

适用于纯展示或单步交互：

- 图片对比节点

### Workbench 节点

适用于复杂交互、编辑器或嵌入式视图：

- 图片蒙板重绘节点
- AI 故事板节点升级版
- AI 360 度全景图节点
- AI 空间模型节点
- Supersplat 查看器
- 全景图浏览器

原则是不要把重交互都塞进通用节点壳层中，而要沿用 `aiStoryboard` 的 workbench 思路。

## 5.5 智能体实现策略

本期智能体只做 `MVP`，不追求一开始就做完全自治。

### 画布对话智能体 MVP

- 能读取当前 workflow、节点列表、文件引用、最近任务历史
- 能回答“下一步怎么做”“该加什么节点”“当前问题出在哪”
- 能输出建议提示词或节点配置草稿
- 如需写回画布，必须经过用户确认

### 平面图规划智能体 MVP

- 输入：平面图、设计目标、风格偏好
- 输出：空间分区建议、功能区说明、推荐节点链路、推荐提示词
- 本期不做 CAD 级精确制图

### AI 项目调研智能体 MVP

- 输入：项目资料、用户问题、已有输出图
- 输出：调研摘要、风格关键词、参考方向、画布节点建议
- 本期优先支持“基于上传资料”的研究，不把外部搜索作为强依赖

## 8. 各模块交付定义

## 8.1 后台数据库架构

本期必须交付：

- 明确 SQL 与 JSON Store 的边界
- 新增 migration 并形成可回放结构
- 扩展文件资产类型
- 为模型管理、快照历史、智能体会话留出稳定结构

验收标准：

- 新旧执行链路不受影响
- 所有新增节点的输入输出都能落入统一文件资产体系
- 任务、快照、智能体记录可以按 `workflowId` 追溯

## 8.2 任务历史

本期必须交付：

- 历史列表页
- 任务详情页
- `workflowId / nodeType / status / 时间范围` 筛选
- `snapshotId` 关联与反查

验收标准：

- 从任一新节点执行结果可追到任务详情
- 从任务详情可回看关联画布快照
- 中台与前台使用同一套任务真源

## 8.3 后端数据管理中台

本期必须交付：

1. 先保 `P0`
2. `P1` 只交 MVP
3. 如工期受压，优先缩减：
   - AI 项目调研智能体
   - 平面图规划智能体高级能力
   - 画布对话智能体写回画布能力
   - AI 空间模型节点的高级导出能力

不建议缩减的模块：

- 数据库架构
- 任务历史
- 中台骨架
- 模型注册
- 图片蒙板重绘

## 10. 风险与控制措施

### 10.1 架构热点风险

风险：

- 新功能继续堆进 `WorkflowContext.tsx`、`Canvas.tsx` 会加剧耦合

措施：

- 新节点逻辑优先落到独立节点目录
- 中台独立到 `backend/admin-web/`
- Agent 逻辑独立为 `api/modules/ai` 或 `api/modules/agents`

### 10.2 Provider 不稳定风险

风险：

- 老张、RunningHub、视频或 3D Provider 响应格式和稳定性可能波动

措施：

- 所有外部调用都必须保留原始快照
- 重试策略、错误映射、最终错误信息统一纳入任务事件流
- 模型注册页支持快速下线故障模型

### 10.3 文件类型扩展风险

风险：

- 全景、PLY、Splat 等新资产类型引入后，预览、下载、回填逻辑可能散乱

措施：

- 统一扩展 `file_assets.file_type`
- 统一文件元数据与 preview contract
- 所有新资产先走文件体系，再走 viewer 嵌入

### 10.4 智能体范围膨胀风险

风险：

- 智能体容易从“建议工具”膨胀成“自动执行系统”

措施：

- 本期只做 MVP
- 所有写回动作必须可确认、可回滚、可审计
- 智能体先复用现有节点，不自建第二套执行系统

## 12. 最终建议

这批需求按项目现状不是不能做，但必须按“底座优先、节点复用、智能体收敛”的顺序推进。

最重要的不是把 15 个功能名义上都挂上去，而是确保到 `2026-06-26` 时，项目能形成下面这条真实闭环：

```text
画布创建
-> 文件进入系统
-> 节点执行
-> 结果回写
-> 任务历史可查
-> 中台可运营
-> 新资产可预览
-> 智能体可辅助下一步操作
```

如果这条闭环打通，本期就是成功的；如果只堆节点数量而没有数据真源、历史可追溯和运营入口，本期结果会很难继续扩展。
